# Lab 02 — Data Loading Policy

## 1. Загальний принцип
Дані з п'яти CSV-файлів завантажуються у PostgreSQL через staging, проходять валідацію та після перевірки публікуються у core.
Початкові записи зберігаються у staging без видалення помилкових рядків.

## 2. Правила валідації
- Ідентифікатори зберігаються як text. Порожні ключі відхиляються.
- Кількість товару повинна бути цілим додатним числом у межах integer.
- Грошові значення повинні бути невід'ємними та відповідати numeric(12,2).
- Допустимі валюти: UAH, USD, EUR.
- Некоректні валюти, зокрема UA H, не виправляються автоматично.
- Дати приймаються у форматі ISO 8601 з часовим поясом або DD/MM/YYYY HH:MM.
- Для DD/MM/YYYY HH:MM використовується часовий пояс UTC.
- Дробові частини секунд довші за шість цифр обрізаються до мікросекунд під час перетворення; початковий запис залишається у staging.
- Для активного товару ціна повинна бути більшою за нуль.
- Для неактивного товару допускається нульова ціна.
- Відсутність необов'язкового значення не замінюється вигаданими даними.

## 3. Дублікати та конфлікти
Для кожного джерела записи порівнюються за бізнес-ключем та вмістом.
- Перший точний запис може отримати статус accepted.
- Наступні точні копії отримують статус duplicate.
- Записи з однаковим бізнес-ключем, але різними значеннями, відхиляються як конфліктна група.
- Технічні поля запуску не використовуються для порівняння бізнес-копій.

## 4. Перевірка зв'язків
Перевіряються такі залежності:
- orders → customers;
- orders → merchants;
- products → merchants;
- order_items → orders;
- order_items → products.
Якщо пов'язаний батьківський запис відсутній або відхилений, дочірній запис також відхиляється.

## 5. Аудит
Кожен вхідний запис отримує один підсумковий статус:

- accepted;
- rejected;
- duplicate.
В аудиті зберігаються run_id, batch_id, source_file, source_row_number, business_key, reason_code, reason та raw_payload.

## 6. Публікація у core
Використовується політика повного snapshot.
П'ять core-таблиць оновлюються в межах однієї транзакції. Успішний запуск завершується COMMIT.
Якщо виникає помилка, виконується ROLLBACK, попередній коректний стан core зберігається, а спроба позначається як failed.
Повторний запуск того самого пакета не повинен змінювати бізнес-стан core.

## 7. Звірка
Для кожного CSV перевіряється рівність:
input_count = accepted_count + rejected_count + duplicate_count.
Кількість прийнятих записів порівнюється з кількістю записів у core.
Також перевіряються зовнішні ключі та суми orders.total_amount і order_items.line_total окремо за валютами.
