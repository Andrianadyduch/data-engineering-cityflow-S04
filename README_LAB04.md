# Лабораторна 4. Надійне отримання даних із файлів і REST API

Це **стартовий комплект, а не готова відповідь**. У `src/lab04/student.py` потрібно реалізувати три функції. Сервер API, запуск, архівування, PostgreSQL-запис і тести вже надані.

## Що отримати від викладача

1. Цей спільний комплект із DOCX-завданням.
2. **Лише свій** `CityFlow_Lab04_SXX.zip`, де XX — 01…10. Усередині є каталог `lab04_variant/`.

Нічого не генеруйте повторно. Виданий CSV-архів — точна копія вашого `batch_01_normal_v1`. API-записи — часовий зріз з уже створених даних CityFlow v1.0. Пакет не містить teacher manifests чи даних інших студентів.

## Куди скопіювати

Продовжуйте той самий репозиторій і БД, що в лабораторних 1–3. Не замінюйте старі каталоги цілком: додайте нові файли з цього комплекту, зберігши попередні.

Додайте правила з `.gitignore.lab04` до власного `.gitignore`. Скопіюйте `data/lab04_variant/credentials.env` як `.env.lab04` у корінь репозиторію. Укажіть власну `DATABASE_URL` навчальної PostgreSQL. Усі поля, крім вашого підключення до БД, уже заповнені для варіанта. Спеціальні символи в паролі URL потрібно percent-encode; не вставляйте справжній пароль у звіт.

## Середовище

Використовуйте Python-середовище попередніх робіт (рекомендовано Python 3.12). У корені репозиторію, з активованим середовищем:

```bash
python -m pip install -r requirements-lab04.txt
```

Коли середовище ще не створено:

```bash
python -m venv .venv
```

macOS/Linux: `source .venv/bin/activate`. Windows PowerShell: `.venv\Scripts\Activate.ps1`. За обмеження execution policy можна запускати `.venv\Scripts\python.exe` замість `python` без активації. Подальші команди запускайте **з кореня репозиторію**, а не з `src/lab04/`.

## 1. Перевірити інфраструктуру (ще без вашої реалізації)

В окремому терміналі:

```bash
python tools/lab04/start_api.py
```

Сервер лишається запущеним; це нормально. Для зупинки — Ctrl+C. Якщо порт 8000 зайнятий, передайте `--port 8001` та змініть `CITYFLOW_API_BASE_URL` у `.env.lab04`.

У другому терміналі:

```bash
python src/lab04/main.py check
python src/lab04/main.py init-db
```

`check` викликає `/api/v1/me`, перевіряє ключ та student_id. `init-db` створює тільки `stg.lab04_records` та `audit.lab04_runs`; нічого не видаляє. PostgreSQL має бути запущена, як у ЛР2. Серверу API Docker не потрібний, хмарні акаунти й платні API не потрібні.

## 2. Реалізувати читання файлу

Дописати `read_file_batch()` у `student.py`. Перевірити:

```bash
python -m pytest -q tests/lab04 -k file
python src/lab04/main.py file
```

`file` тільки копіює ZIP у raw і читає CSV. У БД не записує. Очікується `EXTRACTED_ONLY`, кількості — у `expected_counts.json` вашого варіанта. Помилка з незаповненої функції очікувана, поки ви не виконали відповідний крок.

## 3. Реалізувати HTTP-запити та пагінацію

Спершу `request_page()`, потім `fetch_pages()`:

```bash
python -m pytest -q tests/lab04 -k "retry or timeout or attempts or tls"
python -m pytest -q tests/lab04
python src/lab04/main.py api
```

У комплекті 26 відкритих тестів. Вони підміняють HTTP-відповіді; не використовують PostgreSQL або реальну мережу й не витрачають реальний час на очікування. API-команда, навпаки, використовує живий локальний сервер. Вона має дочекатися всіх сторінок, записати raw і повернути `EXTRACTED_ONLY`.

### Профіль збоїв

У всіх варіантах: перший запит першої сторінки → 429 (`Retry-After: 1`), перший запит другої → 500; повтор успішний. Перезапуск сервера скидає лічильники. Не прибирайте профіль і не змінюйте вихідні файли для обходу тесту. Оригінальні індивідуальні інциденти генератора тут навмисно **не ввімкнені**.

У цьому контракті Retry-After задається цілим числом секунд. Зовнішні HTTP API можуть також передавати дату; таку підтримку можна додати окремо, але вона не є вимогою цієї роботи.

## 4. Спершу перевірити відкат, потім завершити завантаження

До першого успішного `run` виконайте:

```bash
python src/lab04/main.py run --fail-before-commit
```

Команда має завершитися кодом 1, у `audit.lab04_runs` — FAILED, у цільових записах не має бути нового `first_run_id` цієї спроби. Порівняйте кількість рядків до та після. Далі:

```bash
python src/lab04/main.py run
python src/lab04/main.py verify
python src/lab04/main.py run
python src/lab04/main.py verify
```

Перший звичайний `run` додає записи; другий не додає нових. `verify` дає `ok: true`. У другому SUCCESS для кожного джерела `inserted=0`, `already_present=unique`.

**Не очищуйте core або lab03.** Якщо випадково виконали успішний `run` до перевірки відкату, повторіть сценарій на окремій навчальній БД з новими таблицями ЛР4; інакше тест повторного порожнього вставлення не покаже реальний відкат нових записів.

## Значення команд та лічильників

- `file`, `api` — отримання без публікації; не пишуть audit-рядків у БД.
- `run` — обидва джерела, перевірка, одна транзакція публікації.
- `received` — усі отримані записи, включно з повторами.
- `unique` — різні ключі джерела після технічної дедуплікації.
- `duplicates_in_input = received - unique`.
- `inserted` — нові записи поточного успішного запуску.
- `already_present = unique - inserted`.

Payload CSV містить рядкові значення; API payload зберігає типи JSON. В обох випадках усі поля залишаються. Це технічне staging, не DWH і не підтвердження бізнес-коректності. Raw ZIP та JSON bodies не замінюються JSONB.

API-зріз обмежений `occurred_at` 1–7 вересня 2026 включно та `available_at` до 8 вересня 23:59:59 UTC. У реалізації v1.0 верхні межі **включні**. Фільтри не змінюються між сторінками/спробами. Не прирівнюйте кількість API-подій до кількості замовлень; одна доставка має кілька подій, а видимість джерел різна.

## Відомі межі

Одне фіксоване вікно, один активний writer. Автоматичний watermark, backfill, distributed transactions, Kafka, webhooks, CDC, Airflow, Docker і DWH не потрібні. Нові API-поля потрібно зберігати, але міграції нормалізованої схеми не будуються. Кількість рядків — корисна перевірка, не універсальний доказ відсутності всіх пропусків; для навчального зрізу додається незалежна контрольна кількість унікальних ключів.

Драйвер зберігає audit RUNNING до читання джерел. Лише зміни staging + SUCCESS входять в одну DB-транзакцію. Raw-файли не входять у DB-транзакцію та лишаються після відкату. При аварійному завершенні процесу audit може залишитися RUNNING: це не SUCCESS. Різні run_id та raw-каталоги не порушують ідемпотентність бізнес-записів.
